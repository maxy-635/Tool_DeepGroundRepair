\begin{abstract}
Large language models (LLMs) can generate deep learning (DL) programs from natural-language requirements, but the generated programs may contain API-level syntactic issues or fail at runtime because of tensor-shape mismatches. We present the tool realization of \textsc{DeepGroundRepair}, which integrates API-grounded generation, failure localization, and shape-aware repair into an executable workflow. It grounds draft generation in task-relevant API knowledge, localizes upstream API configurations behind tensor-shape failures, and uses runtime tensor shapes to guide parameter repair. Re-execution validates the resulting program. \textsc{DeepGroundRepair} supports TensorFlow, PyTorch, and PaddlePaddle and is intended for DL developers and software engineering researchers working with LLM-generated DL code. The artifact is available at \url{https://github.com/maxy-635/DeepGroundRepair}; the demonstration video link will be added in the camera-ready version.
\end{abstract}

\section{Introduction}
Deep learning (DL) programs must satisfy library-specific API usage constraints and tensor-shape dependencies. LLM-generated DL programs may therefore contain nonexistent or misused APIs and may also fail at runtime because of tensor-shape mismatches. Such failures are difficult to diagnose because the operation reporting a mismatch can be downstream from the API configuration that introduced the incompatible shape.

Existing retrieval-augmented generation (RAG) and execution-feedback-guided repair methods face DL-specific challenges. RAG methods struggle to retrieve relevant APIs due to the gap between high-level task requirements and fine-grained API knowledge \cite{rag}. Meanwhile, traceback-guided repair provides insufficient guidance for resolving tensor-shape mismatches, which account for 77.34\% of runtime failures on average in our prior study \cite{DeepEval}, as their root causes often lie in upstream API configurations and involve complex tensor-shape dependencies. These limitations motivate a DL-specific tool that grounds code generation in verified API knowledge and guides repair through root-cause localization and explicit tensor-shape constraints.

To address these challenges, we present \textsc{DeepGroundRepair}, a tool that integrates API-grounded generation, root-cause localization, and shape-aware repair into a unified \textit{Generate} → \textit{Localize} → \textit{Repair} workflow. Given a natural-language requirement, a target DL library, and an LLM configuration, the tool generates a draft program grounded in retrieved API knowledge. If execution fails, it localizes the root cause using runtime tensor-shape information and performs targeted repair followed by execution validation. The tool also exposes intermediate diagnostic and repair artifacts, allowing users to inspect the generation and repair process.

This paper presents the tool realization of the previously proposed \textsc{DeepGroundRepair} approach. Rather than restating the underlying algorithms, we focus on how its generation--localization--repair backend is used in practice, demonstrated on a representative tensor-shape failure.



\section{\textsc{DeepGroundRepair} Tool Design}

\textsc{DeepGroundRepair} integrates API-grounded generation, failure diagnosis, and shape-aware repair into a unified workflow. As shown in Figure~\ref{fig:workflow}, the tool organizes these stages into an executable pipeline, where generated code and diagnostic information are passed between stages to guide subsequent processing. The workflow is supported by locally deployed LLMs and a library-specific API knowledge base covering TensorFlow, PyTorch, and PaddlePaddle.

\noindent\textbf{API-Grounded Generation.}
Given a natural-language task requirement and a target DL library, \textsc{DeepGroundRepair} recommends task-relevant APIs, verifies their existence, and retrieves corresponding API documentation from the knowledge base. The retrieved knowledge is then provided to the LLM to generate a draft DL program. This stage produces the initial code for subsequent execution and diagnosis.

\noindent\textbf{Failure Diagnosis.}
The tool executes the generated program and captures runtime failures. For tensor-shape mismatches, it combines traceback information with static and dynamic analysis to trace the failure to its upstream API configuration. The diagnosis identifies the root-cause API, suspicious parameters, and relevant tensor shapes. It then masks the suspicious parameters in the generated code, producing parameter-masked code for subsequent repair.

\noindent\textbf{Shape-Aware Repair.}
The tool annotates the parameter-masked code with traced tensor shapes and retrieves relevant shape-related API knowledge. The annotated code and retrieved knowledge are provided to the LLM to guide targeted repair of the identified parameters. The resulting program is re-executed to validate whether the runtime failure has been resolved.

\section{Tool Usage}
\subsection{Supporting Resources}
\noindent\textbf{Implementation and Installation.}
\textsc{DeepGroundRepair} is implemented in Python and supports TensorFlow, PyTorch, and PaddlePaddle. Our experiments were conducted on a server equipped with two NVIDIA V100 GPUs, running CentOS Linux 7.8, Python 3.10, CUDA 12.1, and cuDNN 8.9.5. The DL library versions were TensorFlow 2.16.1, PyTorch 2.11.0, and PaddlePaddle 3.3.0. The artifact provides a Conda environment specification (\texttt{environment.yaml}) for installing the required dependencies, with detailed installation instructions available in the artifact repository.

\noindent\textbf{LLM Deployment.}
\textsc{DeepGroundRepair} supports locally deployed open-weight LLMs through Hugging Face Transformers. The current implementation uses models from the Gemma-3 and Mistral families, covering parameter sizes from 3B to 27B. Users can configure the local model checkpoints in the provided execution scripts to perform API recommendation, code generation, and shape-aware repair.

\noindent\textbf{DL API Knowledge Base.}
\textsc{DeepGroundRepair} incorporates library-specific API knowledge bases constructed from the official documentation of TensorFlow, PyTorch, and PaddlePaddle, containing 3,686, 4,137, and 1,531 API entries, respectively. Each knowledge base provides sparse and dense retrieval indexes to support Stages 1 and 3. Specifically, Stage 1 retrieves API names, signatures, and descriptions for draft code generation, while Stage 3 additionally retrieves parameter descriptions and available tensor-shape transformation formulas to guide inter-path mismatch repair.


\subsection{Tool Configuration and Execution}

\noindent\textbf{Input and Configuration.}
The current prototype uses natural-language task requirements from the DeepEval benchmark \cite{DeepEval}, stored as YAML files under \path{benchmark/DeepEval/}, each containing a \texttt{Requirement} field. Before execution, users configure the target DL library (\texttt{--dlls}), benchmark (\texttt{--benchmark}), LLM checkpoint, experiment ID, and number of generation repeats (\texttt{--repeats}) in the provided scripts. Consistent model and experiment IDs are maintained across the three stages to ensure correct access to intermediate results. The repository also provides preconstructed API knowledge bases under \path{database/}.

\noindent\textbf{Tool Execution.}
The three stages are invoked sequentially through their respective \texttt{run\_main.sh} scripts under \path{run_bashes/step_one/}, \path{run_bashes/step_two/}, and \path{run_bashes/step_three/}. Stage 1 generates draft DL programs and saves them as \texttt{generated\_code.py}, together with API retrieval records. Stage 2 processes the generated programs to diagnose execution failures, producing \texttt{annotated\_code.py} and \texttt{annotated\_code.json}, which contain code and structured diagnostic information for downstream repair. Stage 3 consumes these two artifacts to generate \texttt{repaired\_code.py} and re-executes the repaired program for validation. The stage-specific code artifacts are organized under \path{response/}, with execution logs stored under \path{logs/}. The repository also provides separate evaluation scripts for checking code executability, API-level syntactic issues, and semantic consistency.

\noindent\textbf{End-to-End Effectiveness.}
We use code executability, measured by Code Executability Rate (CER), as the primary effectiveness criterion because successful execution is a fundamental requirement for generated DL programs. As shown in Table~\ref{tab:api_issues}, \textsc{DeepGroundRepair} reduces API-level syntactic issues, including API hallucinations and parameter misuses, by an average of 5.4 issues per 10 programs compared with the four baselines. As shown in Table~\ref{tab:cer}, it achieves the highest average CER across all three DL libraries, with an average relative improvement of 86.0\% over the baselines. Compared with the two self-debugging baselines, it further improves Semantic Consistency Rate (SCR) by an average of 16.7\%, indicating better
preservation of program structure during repair.

\noindent\textbf{Token Efficiency.}
Compared with the generation-only baselines (B1--B2), \textsc{DeepGroundRepair} incurs 25.0\%--63.0\% higher token cost while improving CER by 54.0\%--279.5\%. More notably, compared with the self-debugging baselines (B3--B4), it reduces token cost by 18.5\%--33.9\% while improving CER by 13.7\%--77.0\%. These results demonstrate that \textsc{DeepGroundRepair} achieves higher executability with lower token cost than traceback-guided self-debugging approaches. Further experimental results and detailed analyses are presented in the associated research study\cite{deepgroundrepair}.

\section{Related Work}
\textbf{Bugs and Constraints in Deep Learning Programs.}
Deep learning programs compose library-specific APIs into computation graphs, so correctness depends on both valid API usage and compatible tensor transformations. Empirical evidence on LLM-generated DL programs reports frequent API hallucinations, parameter misuses, and runtime tensor-shape mismatches; the latter constitute the predominant class of execution failures in the studied settings \cite{DeepEval}. These observations motivate tools that expose DL-specific API and shape constraints during both generation and repair.

\textbf{Retrieval-Augmented Code Generation.}
Retrieval-augmented generation (RAG) grounds an LLM's output in external knowledge \cite{rag}. API documentation can provide signatures, parameter descriptions, and usage constraints, while relevant code retrieval can provide reusable implementation context. However, a natural-language DL requirement describes modeling intent at a higher level than an individual API, so a direct retrieval query may return irrelevant documentation. \textsc{DeepGroundRepair} addresses this gap by recommending and verifying task-relevant APIs before retrieving library-specific knowledge for generation and repair.

\textbf{Repair of LLM-Generated Code.}
Feedback-guided methods use execution results or self-generated explanations to iteratively revise generated programs; self-debugging is a representative example \cite{selfrepair}. Such feedback is useful for general code repair, but a raw traceback often identifies only the downstream operation where a DL shape mismatch becomes visible. \textsc{DeepGroundRepair} complements feedback-guided repair with root-cause localization and explicit runtime tensor-shape guidance, thereby targeting the upstream API configuration and parameter values that need to be changed. The present paper focuses on the executable realization and usage of this generation--localization--repair workflow, while the underlying framework is described in the associated research study \cite{deepgroundrepair}.


\section{Conclusion}
This tool paper presents the executable realization of \textsc{DeepGroundRepair} for LLM-generated deep learning programs. Starting from a natural-language requirement, the tool grounds draft generation in library-specific API knowledge, diagnoses the upstream causes of tensor-shape failures, produces a shape-aware repair, and validates the repaired program through re-execution. The current implementation supports TensorFlow, PyTorch, and PaddlePaddle, and exposes intermediate artifacts such as retrieved APIs, failure traces, localized parameters, runtime shapes, and repaired code so that users can inspect and reproduce the workflow.

Across the evaluated model-level tasks, the associated study reports fewer API hallucinations and parameter misuses, an average relative improvement of 86.0\% in code executability, and a 16.7\% average improvement in semantic consistency over traceback-guided self-debugging baselines \cite{deepgroundrepair}. These results support the practical value of combining API grounding, root-cause localization, and shape-aware repair in one tool workflow. Future work will extend the tool with lightweight constraint checking during generation, stronger analysis for complex tensor flows, adaptive multi-step repair for interacting faults, and diagnosis of additional failure types such as dtype or device incompatibilities, numerical instability, and training-time failures.
